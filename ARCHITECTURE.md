# Architecture and decisions

A modular monolith runs one board per application instance. `backend/lab.py` owns process and storage lifecycle. `emulator/qmp.py` keeps QMP private and serializes requests while recording events. `emulator/serial.py` reads a QEMU Unix chardev, captures boot output, and bridges bytes to a raw Linux PTY. `emulator/profiles.py` defines board and peripheral capability metadata. React uses REST state only. Shell access uses host PTYs or SSH; no browser stream is exposed.

Power: OFF → STARTING → RUNNING → STOPPING → OFF; process failures become ERROR. RUNNING means QEMU runs, not that Linux finished booting. Actual boot progress is visible in serial. Graceful shutdown for the bundled guest is SSH guest poweroff, with no force fallback. Custom images shut down from their own external terminal; management credentials are not injected. Reset is QMP system_reset; there is no auto-restart after guest failure. Natural exit is reaped; shutdown terminates and, if necessary, kills/reaps the child.

Media: AVAILABLE → INSERTED → GUEST_RUNNING → INSERTED → AVAILABLE (ejected). No HOST_MOUNTED or EJECT_PENDING is exposed because host mounts and live boot-disk ejection are unsupported. SQLite persists identity and insertion; qcow2 overlays persist student writes. QEMU owns the writable image while running. Media mutations run under the lab lock. Reset prepares replacement storage before deleting the prior overlay.

UART modes are disconnected and host. The backend is the sole QEMU chardev reader and bridges it to a raw host PTY. Host terminal exclusivity uses the documented flock command. The application retains bounded internal boot history and serial.log for diagnostics, without exposing them as an in-browser console. Browser UART mode is rejected; legacy serial/display WebSocket routes close with policy code 1008. There is no browser writer, observer, noVNC proxy or terminal component. QEMU UART bytes remain real and bidirectional through the host endpoint.

Network: SLIRP NAT, fixed locally administered MAC, loopback-only TCP forward. QMP set_link controls the virtio NIC or Pi-mode USB Ethernet adapter. Guest DHCP normally assigns 10.0.2.15 but the UI does not claim it has detected the address. Guest-to-host uses 10.0.2.2. No TAP privileges or host routing changes.

Security boundary: local trusted user. HTTP Host and browser Origin checks block cross-origin controls/DNS rebinding; no remote authentication service is provided. No QMP endpoint is exposed to the browser, no client-provided commands execute, and import uses streamed bytes or explicit local regular-file paths, copied under generated names. Raw ext4/MBR/GPT layouts are validated. Uploaded qcow backing chains are never opened. Each import gets an immutable baseline and writable overlay; copied boot artifacts and command line are stored per disk. FAT boot extraction is unprivileged and does not mount the guest. QEMU and guest images are not a hardened sandbox for hostile inputs. Only run trusted teaching images. A runtime flock prevents duplicate app instances using the same metadata. Processes are reaped on ordinary shutdown; SIGKILL or host power loss can bypass cleanup and require manual process inspection.

The frontend has no embedded terminal or display viewer, and explicitly identifies unimplemented GPIO controls. Future board drivers can use the profile registry and peripheral metadata, but no dynamic third-party plugin loading is implemented.

Display hardware: the bundled virt guest retains virtio-gpu-pci and its explicitly bound virtio keyboard. Custom kernels omit those optional devices; the Pi profile has its own framebuffer model. QEMU's private VNC Unix socket is not proxied to the browser. At the user's request, all browser console viewers and keyboard paths were removed. The web UI only manages resources and displays metadata/copyable host commands.

`scripts/prepare_display.py` still prepares the managed guest's framebuffer support without rewriting base.raw. Existing guest devices and tty1 configuration are preserved. Browser display support can be reconsidered separately when a graphical desktop is provided; text consoles remain a host-terminal workflow.
